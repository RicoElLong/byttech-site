## Выбранный API и серверный интерфейс

Рабочий путь для нового сайта: `POST /api/requests` отдельного FastAPI-приложения
в `bot-tech/web_api.py`. Сайт не использует `/api/leads` донора и старый webapp.py.
Старый `/api/leads` остаётся в доноре для его клиентов; пример Nginx нового
сайта наружу открывает только новый маршрут и его config.

`GET /api/requests/config`: `ready` и `consent_version=pd-2026-11-09-v1`.
Браузер включает отправку только при совпадении версии и ready=true.

Тело POST: `submission_id` UUID, `brand`, `problem` из вариантов донора,
`name`, `phone`, необязательный `comment`, пустое `website`,
`personal_data_consent=true`, `consent_version=pd-2026-11-09-v1`.
Ответ: `accepted=true`, положительный целочисленный `request_id`.
Путь, имена полей согласия, версия и числовой тип ответа БытТех сохранены.
Это callback без отдельных preferred_date/preferred_time; старую систему
бронирования нельзя переключать на него без отдельной миграции клиентов.

Сервер нормализует телефон, проверяет обязательные поля, варианты и согласие,
Origin/Content-Type, тело до 16 КиБ и частоту. UUID с тем же содержимым возвращает
ту же заявку и не добавляет уведомление. Другие данные с тем же UUID отклоняются.
Повторное обращение с тем же телефоном обновляет карточку. Версия и время
согласия сохраняются сервером. Заявка и outbox записываются одной транзакцией.
Ошибка доставки не отменяет заявку; отдельный worker повторяет уведомление
и не пересылает его уже получившим администраторам.

Сообщение Telegram содержит только номер и ссылку на карточку с непредсказуемым
UUID. Карточка требует HTTP Basic по HTTPS, экранирует данные, no-store/noindex.
Имя, телефон, марка, проблема и комментарий не включаются в уведомление.
Токен, ID получателей и пароль задаются только на сервере. Контакты в URL,
аналитику, localStorage и консоль браузера не записываются.

Review-патч сервера: `deploy/patches/bot-tech-requests.patch`. Он включает код,
новые тесты и документацию. Изменения также находятся в `/workspace/bot-tech`.
Для переноса: проверить базовый коммит, затем `git apply --check <patch>` и
`git apply <patch>` в чистом checkout этой версии. Не применять повторно
к уже изменённому checkout. Не переносить сервер/базу/секреты в web-каталог.

## Настройка и внешние условия запуска

Публичный фронтенд:

- `SITE_URL`: подтверждённый полный HTTPS URL, при необходимости с подпапкой.
- `OWNER_NAME`, `OWNER_INN`, `OWNER_ADDRESS`, `OWNER_PHONE`, `OWNER_EMAIL`.
- `REQUEST_API_URL=https://<подтверждённый-api>/api/requests`.
- `WEB_DOCUMENTS_CONFIRMED=1` только после согласования сведений и документов.

Сервер (значения в защищённых настройках, не в репозитории):

- `WEB_FORM_ENABLED=true`, `WEB_DOCUMENTS_CONFIRMED=1`.
- `WEB_SITE_ORIGIN`: HTTPS origin фронтенда без пути; `WEB_API_PUBLIC_URL`:
  HTTPS origin API/защищённой карточки.
- `WEB_OPERATOR_NAME`, `WEB_OPERATOR_ADDRESS`, `WEB_OPERATOR_EMAIL`.
- `WEB_DATA_LOCATION_CONFIRMED=ru` только после фактической проверки размещения.
- `WEB_DATABASE_PATH`: абсолютный путь вне публичного root и каталога релиза.
- `BOT_TOKEN`, `ADMIN_IDS`, `WEB_ADMIN_USER`, `WEB_ADMIN_PASSWORD` (не менее 20 символов).

Текущие реквизиты, хостинг и основной домен не подтверждены. Отправка выключена.
Canonical и production sitemap поэтому не создавались с выдуманным адресом:
механизм проверен с example.test только во временных тестовых сборках.
Необходимо согласовать документы (в том числе 30-дневное хранение и обработку
технических данных GitHub Pages) перед установкой флагов. Суммы существующего
прайса сохранены, но их подтверждение владельцем перед релизом остаётся обязательным
по web/PRICE_SOURCE.md.

После настройки HTTPS на production проверить 6 статей, 404, canonical/sitemap,
корневой robots.txt (особенно если используется подпапка GitHub Pages),
CORS, доступность бота, авторизацию карточек, фактическое хранение/удаление,
резервные копии и доставку уведомления. Никакие реальные заявки, настройки
рабочего домена, секреты или опубликованный сайт в этой задаче не менялись.
